# QA Atlas — AI-платформа для тестирования требований и исходного кода

**Кейс № 9 · ТПУ · Готовый Docker-проект**

QA Atlas помогает QA-инженеру пройти путь от документа с требованиями до проверяемых автотестов: загрузить требования и исходники, подготовить Gherkin-сценарии и тестовый код, выполнить pytest/Playwright в изолированном окружении, увидеть PASS/FAIL и покрытие исходников, исследовать ошибку с помощью ИИ и выгрузить результаты. Интерфейс ориентирован в том числе на пользователя без навыков программирования.

## Возможности

| Компонент | Что реализовано |
| --- | --- |
| Работа с требованиями | Импорт PDF, DOCX, Markdown и TXT; извлечение требований, просмотр и привязка к тестам |
| Объёмные документы | Фоновая обработка через очередь |
| Генерация | Gherkin Given/When/Then, Python pytest, JavaScript Playwright; черновики и уточнения |
| Исполнение | Изолированный Docker Runner, журнал pytest/Playwright, PASS/FAIL, история прогонов |
| Покрытие | `coverage.py` для Python; построчная подсветка выполненных и невыполненных строк |
| Прослеживаемость | Связи REQ ↔ TC, матрица требований, аналитика и рекомендации по пробелам покрытия |
| AI Bug Detective | Анализ ошибок и traceback: объяснение, вероятная причина, место дефекта, возможное исправление, уверенность |
| Баг-репорты | Отчёт с шагами воспроизведения, фактическим результатом, traceback и гипотезами ИИ |
| Другие AI-инструменты | Генерация тестовых данных, выделение ограничений, поиск похожих тестов |
| Семантический поиск | Настоящие embeddings через API Yandex/OpenAI, хранение и поиск в PostgreSQL с `pgvector` |
| Экспорт | Тесты `.feature`, `.py`, `.js`, архив проекта и результаты прогонов |

**Ограничения:** AI-предложения требуют проверки человеком; привязка теста к требованию сама по себе не доказывает его выполнение. Сканированные PDF без текстового слоя не распознаются. Runner выполняет Python и JavaScript, но не Java/JUnit; браузерное покрытие Playwright не измеряется. Семантический поиск возвращает ближайшие тексты по сходству, а не юридическое/формальное подтверждение соответствия.

## Архитектура

```text
Браузер (React + TypeScript + Vite)
             │ HTTP / REST
             ▼
Backend (Node.js 24)
   ├── PostgreSQL 16 + pgvector — проекты, тесты, история и векторы
   ├── Redis 7 — очередь фоновых задач
   ├── ML-service (Python / FastAPI) — разбор документов и ИИ
   │      └── Yandex AI Studio / совместимый API
   └── Docker Runner — изолированный запуск автотестов
```

Всё поднимается через `compose.yaml`. Фронтенд собирается в образ backend и обслуживается им по адресу `http://localhost:8080`.

## Системные требования

- Docker Engine / Docker Desktop с **Linux-контейнерами** и **Docker Compose v2**.

- Доступ к реестрам Docker для первоначальной загрузки образов.

- Практический ориентир для проверяющего: **4 CPU, 8 ГБ RAM, 10 ГБ свободного места**. Строгие минимальные требования нагрузочно не измерялись.

- Для AI-функций: действующий ключ провайдера, доступная модель и квоты API. Вызовы провайдера могут тарифицироваться.

## Быстрый запуск с нуля

1. Склонируйте репозиторий (или распакуйте исходники) и перейдите в его корневой каталог:

   ```bash
   git clone https://github.com/keliamis/b2b-qa-atlas.git
   cd b2b-qa-atlas
   ```

   Если исходники скачаны ZIP-архивом, команду `git clone` пропустите. Не требуется вводить URL, пока репозиторий не опубликован.

2. Создайте локальную конфигурацию:

   **Windows PowerShell**

   ```powershell
   Copy-Item .env.example .env
   notepad .env
   ```

   **Linux / macOS**

   ```bash
   cp .env.example .env
   ```

3. В `.env` задайте свои `ML_TOKEN`, `POSTGRES_PASSWORD`, `OPENAI_API_KEY`, `OPENAI_MODEL`, `YANDEX_FOLDER_ID`. Пример настройки ниже.

4. Запустите все сервисы:

   ```bash
   docker compose up -d --build
   ```

5. Проверьте состояние:

   ```bash
   docker compose ps
   docker compose logs --tail=80 backend ml-service runner
   ```

6. Откройте **http://localhost:8080**. После создания аккаунта войдите в интерфейс. Предустановленного аккаунта нет.

   Проверка REST API без авторизации:

   ```bash
   curl http://localhost:8080/health
   ```

   Ожидается JSON со `status: "ok"`. При первом запуске дождитесь готовности healthcheck и загрузки образов.

### Переменные окружения

`.env.example` — документированный шаблон **без действующих ключей**. Для запуска с Yandex AI Studio основные поля выглядят так (замените значения-плейсхолдеры на собственные):

```dotenv
PUBLIC_ORIGIN=http://localhost:8080
ML_TOKEN=REPLACE_WITH_A_LONG_RANDOM_TOKEN
POSTGRES_PASSWORD=REPLACE_WITH_A_STRONG_DATABASE_PASSWORD
AI_PROVIDER=yandex
OPENAI_BASE_URL=https://ai.api.cloud.yandex.net/v1
OPENAI_API_KEY=YOUR_YANDEX_API_KEY
OPENAI_MODEL=gpt://YOUR_FOLDER_ID/deepseek-v4-flash
EMBEDDING_PROVIDER=yandex
YANDEX_FOLDER_ID=YOUR_FOLDER_ID
EMBEDDING_API_KEY=
EMBEDDING_BASE_URL=https://ai.api.cloud.yandex.net/foundationModels/v1
EMBEDDING_MODEL=emb://YOUR_FOLDER_ID/text-search-doc/latest
EMBEDDING_QUERY_MODEL=emb://YOUR_FOLDER_ID/text-search-query/latest
EMBEDDING_DIMENSIONS=
```

- `OPENAI_*` — настройки текстовой модели для генерации и AI Bug Detective.

- `EMBEDDING_*` — отдельные модели для поиска по смыслу. При `AI_PROVIDER=yandex` и пустом `EMBEDDING_API_KEY` backend может использовать `OPENAI_API_KEY`.

- `YANDEX_FOLDER_ID` — идентификатор **своего** каталога Yandex Cloud, не ID проекта QA Atlas.

- `ML_TOKEN` — секрет внутренней связи контейнеров. Не используйте значение-пример в реальном развёртывании.

- `POSTGRES_PASSWORD` — пароль БД. **Не меняйте его в уже созданной базе простым изменением `.env`**: это не изменит пароль внутри существующего тома PostgreSQL.

Для другого OpenAI-совместимого провайдера задайте поддерживаемый endpoint и доступную модель. **Модель чата не является моделью эмбеддингов**. Генерация и семантический поиск требуют разных API-возможностей.

## Проверка проекта за 10 шагов

Порядок рассчитан на демонстрацию ключевых функций жюри. Доступность Yandex API и результат генерации зависят от выбранной модели и квот; pytest и покрытие доступны и для вручную подготовленного тестового кода.

1. **Откройте интерфейс.**

Зарегистрируйте аккаунт, войдите и создайте новый проект, например `TPU QA Demo`.

2. **Импортируйте документ с требованиями:**

Загрузите собственный документ с функциональными требованиями в формате PDF, DOCX, TXT или Markdown. QA Atlas автоматически извлечёт текст, выделит требования и сохранит их в проекте для дальнейшей генерации тест-кейсов.

Для проверки обработки больших документов рекомендуется использовать файл объёмом более 50 страниц. Дождитесь завершения фоновой задачи импорта и убедитесь, что требования корректно отображаются в интерфейсе.

3. **Добавьте исходный код:**

Загрузите исходный код собственного приложения или отдельного программного модуля, поведение которого описано в импортированных требованиях. QA Atlas использует загруженный код для формирования исполняемых автотестов, проверки результатов и анализа покрытия исходных строк.

4. **Сгенерируйте тесты.**

Выберите несколько конкретных требований, фреймворк `Python · pytest`, задайте число сценариев и включите генерацию кода. Дождитесь фоновой задачи; проверьте Given/When/Then, ожидаемые значения и связь с исходным REQ. AI-результат сохраняется как черновик и может потребовать ручного уточнения.

5. **Проверьте корректность сгенерированных тест-кейсов.**

Выберите несколько требований из загруженного документа и сгенерируйте для них тест-кейсы. Проверьте, что сценарии Gherkin соответствуют исходным требованиям, содержат конкретные предусловия, действия и ожидаемые результаты.

Особое внимание рекомендуется уделить позитивным, негативным и граничным сценариям. При наличии требований к валидации входных данных проверьте обработку некорректных значений и ожидаемых исключений.

6. **Проверьте обнаружение дефектов.**

Используйте исходный код приложения, поведение которого описано в загруженных требованиях. Создайте или сгенерируйте автотест, проверяющий конкретное бизнес-правило.

Для проверки механизма обнаружения ошибок рекомендуется использовать тестируемый модуль с заранее известным отклонением от требований. Убедитесь, что QA Atlas выявляет несоответствие между ожидаемым и фактическим результатом.

7. **Запустите автотесты и изучите покрытие кода.**

Запустите подготовленные автотесты. Проверьте статусы PASS/FAIL, результаты отдельных проверок, журнал выполнения, traceback при возникновении ошибок и историю запусков.

Откройте отчёт о покрытии исходного кода и убедитесь, что выполненные и непокрытые строки отображаются корректно. Процент покрытия зависит от загруженного кода и выбранного набора тестов.

8. **Проверьте AI-анализ ошибок и создание баг-репортов.**

После выполнения теста со статусом FAILED нажмите «Анализировать ошибку с ИИ».

При настроенном AI-провайдере QA Atlas сформирует объяснение ошибки, укажет вероятную причину, предполагаемое место дефекта, рекомендацию по исправлению и уровень уверенности.

Затем нажмите «Создать баг-репорт». Проверьте, что отчёт содержит информацию о конкретном запуске, фактические результаты, traceback, код теста и читаемые гипотезы ИИ. Вывод модели следует рассматривать как рекомендацию, требующую проверки.

9. **Проверьте несколько независимых сценариев.**

Повторите тестирование для других требований или функций тестируемого приложения. Желательно использовать разные классы проверок: граничные значения, расчёты, валидацию, обработку исключений и корректность бизнес-логики.

10. **Проверьте семантический поиск и экспорт.**

В разделе «Покрытие» → «Поиск требований по смыслу» нажмите «Построить / обновить индекс». После завершения фоновой индексации введите запрос на естественном языке, связанный с содержанием загруженных требований.

Проверьте, что QA Atlas возвращает наиболее близкие по смыслу требования и отображает показатели сходства. Для работы этой функции необходимо предварительно настроить провайдер эмбеддингов.

Затем экспортируйте созданные тестовые артефакты и проверьте содержимое файлов .feature, .py и .js при наличии соответствующих сценариев и автотестов.

### Демонстрационные материалы

Для быстрого знакомства с QA Atlas в репозитории представлены демонстрационные материалы:

`examples/long-document/requirements_51_pages.pdf` — PDF-документ на 51 страницу с тестовыми требованиями.

`examples/long-document/rule_engine.py` — Python-модуль, реализующий соответствующие бизнес-правила.

`examples/long-document/test_rule_engine.py` — готовые автотесты для проверки модуля.

В демонстрационном модуле намеренно предусмотрены два дефекта: неправильная обработка граничного значения для REQ-025 и ошибочная ставка комиссии для REQ-051.

Эти материалы позволяют воспроизвести полный цикл тестирования — от импорта требований и генерации сценариев до выполнения pytest, обнаружения ошибок, анализа покрытия кода и формирования баг-репортов.

Использование демонстрационных файлов необязательно. Проверяющие могут выполнить все основные действия на собственных документах и соответствующем им исходном коде.

## REST API

QA Atlas предоставляет REST API для управления проектами, требованиями, тест-кейсами и результатами выполнения автотестов.

API используется веб-интерфейсом приложения и может применяться для интеграции с внешними системами. Большинство операций требуют авторизации.

### Основные возможности API

| Возможность | Endpoint |
|---|---|
| Проверка доступности | `GET /health` |
| Авторизация | `POST /auth/login` |
| Получение проектов | `GET /api/projects` |
| Импорт документов | `POST /api/projects/:id/documents` |
| Генерация тест-кейсов | `POST /api/projects/:id/generate` |
| Запуск автотестов | `POST /api/projects/:id/auto-runs` |
| Получение результатов запусков | `GET /api/projects/:id/auto-runs` |
| Экспорт результатов | `GET /api/projects/:id/export` |

### Быстрая проверка API

После запуска приложения выполните:

```bash
curl http://localhost:8080/health
```

API должен вернуть успешный ответ о состоянии сервиса.

Для работы с защищёнными маршрутами необходимо предварительно авторизоваться через веб-интерфейс или API.

**Примечание:** генерация, импорт документов и запуск автотестов выполняются асинхронно. Статус фоновых операций можно отслеживать через интерфейс приложения.

Для полноценного тестирования рекомендуется использовать веб-интерфейс QA Atlas, который предоставляет доступ ко всем основным функциям без необходимости отправлять HTTP-запросы вручную.

## Запуск тестов самого проекта

CI-конфигурация находится в `.github/workflows/ci.yml` и запускает проверки Node.js и Python. Для локального исполнения без Docker нужны Node.js 24 и Python 3.12:

```bash
npm ci
npm run check:syntax
npm run typecheck
npm run build
npm test
python -m pip install -r ml-service/requirements.lock.txt pytest coverage
python -m pytest ml-service/tests runner -q
```

Часть тестов runner требует Docker или дополнительных зависимостей. Успешность конкретного CI-прогона смотрите во вкладке GitHub Actions; **наличие тестов не означает, что они запускались на машине проверяющего**.

## Если что-то пошло не так

| Ситуация | Действие |
| --- | --- |
| Не открывается `localhost:8080` | `docker compose ps`, `docker compose logs --tail=100 backend` |
| Не завершилась загрузка PDF | Проверить фоновые задачи и `docker compose logs --tail=100 ml-service backend` |
| AI Bug Detective не отвечает | Проверить ключ, модель и квоты; `docker compose logs --tail=100 ml-service backend` |
| Семантический поиск отключён | Проверить `EMBEDDING_PROVIDER`, модели, ключ, PostgreSQL/pgvector; затем построить индекс |
| Embeddings API: HTTP 429 | Ограничение квоты/скорости провайдера; не запускать параллельные индексации, проверить квоты Yandex |
| Индекс ещё строится | Дождаться завершения фонового задания; поиск включается после готовности |
| Runner не выполняет тесты | `docker compose logs --tail=100 runner backend`, проверить сборку образа `qa-atlas-worker:1` |
| Покрытие ниже цели | Уточнить набор запущенных тестов и реально исполняемые ветви; нельзя считать PASS доказательством полного покрытия |

В случае изменения кода запускайте `docker compose up -d --build`. Для просмотра состояния: `docker compose ps`. Для остановки без удаления пользовательских данных: `docker compose down`.

**Не запускайте `docker compose down -v`** — эта команда удалит тома, включая данные PostgreSQL. Для резервной копии текущей БД используйте:

```bash
docker compose exec -T postgres pg_dump -U atlas -d atlas > atlas-backup.sql
```

## Безопасность и ограничения развёртывания

- `.env`, токены, сессионные cookie, дампы БД и персональные данные не должны попадать в публичный репозиторий.

- При утечке ключа Yandex Cloud либо `ML_TOKEN` ключ необходимо отозвать/перевыпустить.

- Runner использует `/var/run/docker.sock` для запуска изолированных заданий. Это **привилегированный компонент**, поэтому проект следует развёртывать только в доверенной среде с ограниченным доступом к Docker host; для общедоступного многопользовательского сервиса требуется отдельный аудит и усиление изоляции.

- Демонстрационные дефекты в `examples/long-document/rule_engine.py` оставлены намеренно для проверки обнаружения ошибок, а не для эксплуатации в прикладном финансовом сервисе.

- Приложение не выполняет автоматически предлагаемые ИИ исправления кода. Их проверяет человек.
