# QA Atlas 0.5.3 — проверка качества и адресные исправления

Основание: исходный ZIP QA Atlas 0.5.2, пользовательское техническое задание и **официальные слайды 33–35** презентации кейс-чемпионата. На слайде 35 перечислено 7 критериев приёмки. Не путать техническое задание на улучшение продукта с официальными критериями.

## Состояние по семи критериям задачи № 9

| Официальный критерий | Где реализован | Фактический статус |
|---|---|---|
| Gherkin Given / When / Then | `ml-service/app/generator.py` | Реализовано, синтаксис проверяется. Реальная модель в этом окружении не вызывалась. |
| Python pytest или JS Playwright/Cypress | `generator.py`, `runner/worker.py` | Генерация pytest + Playwright, проверка синтаксиса, выполнение поддерживаемых модулей. Cypress не требуется при выборе Playwright. Полный Docker-прогон не проверен здесь. |
| Визуализация покрытых и непокрытых участков | `frontend/src/AutoRuns.tsx` | Реализовано на основе отчётов: строки, подсветка, источник и снимок тестов. Браузерная отрисовка после изменений не проверена. |
| Интеграция coverage.py / Istanbul и процент | `runner/worker.py` | Python `coverage.py`, JS `c8` (Istanbul JSON). Процент рассчитывается по измеренным исполняемым строкам, **не** по количеству тестов. |
| Экспорт `.feature`, `.py`, `.js` | `frontend/src/AutoRuns.tsx`, `backend/src/index.mjs` | Реализовано для имеющихся артефактов. |
| QA-дашборд: количество, покрытие, успешность | `RunMetrics` | Реализовано; устаревший процент больше не отображается как актуальный. |
| `docker-compose up --build` | `compose.yaml`, `deploy/`, `runner/` | Изменён граф сборки: worker-image строится при обычном `docker compose up --build`. **Перед запуском по-прежнему требуется создать `.env`**. Docker не доступен в среде проверки. |

### Основные изменения относительно 0.5.2

1. Полная переработка верстки авторизации: отдельный адаптивный двухколоночный экран с мобильной компоновкой, фокусами, полями одинаковой ширины, показом пароля и индикацией ошибок. Самостоятельная регистрация уже поддерживалась сервером в 0.5.2; механизм сохранён.
2. Генератор не сохраняет как исполняемые пустые/синтаксически некорректные pytest или Playwright тесты; проверяются Python AST, синтаксис JS через `node --check` и наличие теста с проверкой результата. Только для невалидных случаев разрешена **одна** повторная генерация, без повторного принятия уже успешных сценариев.
3. Дополнительная проверка JS в изолированном worker непосредственно перед его выполнением.
4. Отмена задания прерывает запрос backend к сервису обработки, освобождая очередь от ожидания полного HTTP-таймаута.
5. Исправлено поведение `login` при ошибочном JSON-теле (`null`, массив, число): вместо внутренней ошибки возвращается отказ в авторизации.
6. В статистике устаревшего прогона больше не показывается процент покрытия как актуальный; его исторический результат доступен в деталях.
7. Worker-image включён в обычную Docker Compose сборку; `runner` ожидает успешного завершения build-only сервиса.
8. Добавлены регрессионные тесты для валидации ответа модели, повторной генерации, отклонения некорректного JS и некорректного JSON при входе.
9. Runner теперь возвращает результаты отдельных pytest/Playwright проверок (название, статус, длительность, сообщение об ошибке); UI отображает их в раскрываемом списке.
10. Экранированные последовательности внутри корректного JS-кода больше не переписываются как физические переводы строк.

### Не реализовано / риски перед публичным использованием

- Не добавлены email verification, сброс пароля по SMTP, MFA; UI не рисует фиктивные кнопки.
- Роли проекта текущего пилота: owner, tester, viewer, а не отдельные Owner/Admin/Member/Viewer.
- Нет полноценного механизма автоматического измерения покрытия внешнего браузерного SPA, Java/JUnit runner, сборки пользовательского TypeScript, произвольной установки пакетов, sandbox-hardened VM для недоверенных пользователей.
- SQLite и внутренняя очередь Node остаются архитектурными ограничениями. Большой многопользовательский SaaS требует отдельно спроектированных БД, очереди и изолированного runner-хоста.
- Контроллер runner имеет доступ к Docker socket, что делает его **привилегированным**; контейнеры пользовательских тестов изолированы, но это не сертификат безопасности публичного исполнения произвольного кода.
- Импорт сканированных PDF без текстового слоя не обрабатывается: OCR отсутствует.
- Архивирование проектов и восстановление из UI, branch coverage и сравнение прогонов ещё не реализованы.
- Интеграция собственных пользовательских репозиториев с GitHub Actions/CI отсутствует; CI проверяет **сам QA Atlas**.

## Обновление без потери данных (PowerShell)

1. В старой установленной папке создайте резервную копию: `docker compose exec backend node backend/src/backup.mjs`. Сохраните файл резервной копии в отдельном месте.
2. Распакуйте **новый архив**. Скопируйте сюда прежний `.env` (не публикуйте ключи и `ML_TOKEN`). Если установка чистая: `python scripts/init_env.py`, затем добавьте ключ, URL модели и модель в `.env`. Убедитесь, что `PUBLIC_ORIGIN` соответствует адресу сайта.
3. Запустите Docker Desktop (Linux containers). Из новой папки выполните `docker compose up -d --build --wait` — теперь сборка worker-image входит в состав обычного `up --build`. При ошибке проверьте `docker compose logs --tail=100 backend ml-service runner`.
4. `docker compose exec backend node scripts/check_runner.mjs` — реальная проверка Pytest и Playwright в Docker. Она необходима перед демонстрацией.
5. Откройте `/login` и зарегистрируйте отдельного тестового пользователя. Создайте проект, загрузите требования и исходники двумя отдельными полями, сгенерируйте и запустите автотесты, проверьте покрытие/экспорт/удаление.
6. Проверьте изоляцию: второй пользователь без приглашения не должен видеть проект первого. Не выполняйте `docker compose down -v` (удаляет тома с данными).

**Статус:** передан обновлённый исходный проект и подтверждены перечисленные локальные проверки. Это не означает, что полный production-grade аудит или интеграционные проверки в Docker завершены.
